Tiny Compiler in Java · Part I

Chapter 1: Lex Luther

Building the tokenizer: breaking raw input into discrete tokens, managing Java's TokenType Enums, and handling newline detection.

We are forming our language based on the BASIC dialect. Similar to the syntax scope of the original article by Austin Henley, we will maintain the core operations while preparing the ground for custom data structures down the line.

Our language will support a standard suite of basic operations expected from a foundational programming language:

  • Numerical variables
  • Basic arithmetic (addition, subtraction, multiplication, division)
  • If statements and branch conditions
  • While loops
  • Printing text and numbers
  • User input for numeric values
  • Labels and goto jumps
  • Single-line and block comments

Reference: austinhenley.com/blog/teenytinycompiler1.html ↗

In this chapter, we implement the Lexer (or Tokenizer). Its responsibility is straightforward: take raw source code as a stream of characters, break it into meaningful words, and classify whether each token is a keyword, identifier, whitespace, or operator.

Reading the Next Character

We begin by maintaining a pointer to our current position in the source text and consuming characters sequentially.

Peeking Ahead

Peeking allows us to inspect the subsequent character in the stream without advancing our internal pointer. This is critical for operators that span multiple characters (like ==, <=, or comments).

Running the Lexer

With basic pointer advancement and character inspection in place, we run the initial lexer loop. Now, we need a formalized classification system for the tokens we extract.

The Token Type Enum

Building the token table can feel repetitive, and while production-grade compilers typically employ table-driven lexer generators (like Flex or ANTLR), implementing this by hand gives an unmatched mental model of the lexical phase.

Java’s JIT compiler can optimize arithmetic operations using native CPU instructions, bringing execution performance closer to low-level languages like C—even if we don’t manually control memory at the pointer level.

Another everyday example of optimization is Python's NumPy: calling np.dot(A, B) is dramatically faster than a pure Python loop because NumPy delegates down to vectorized C and BLAS under the hood.

Even when we are simply relabeling symbols—stating that the character + maps to the token PLUS—it matters. In systems programming, representation is everything.

We define our token types using a strongly typed Java enum. Enums in Java are full classes, which enables clean, optimized switch logic during parsing.

Whitespace & Comments

In Java, unlike Python, we explicitly handle newline characters (\n). We append an explicit newline at the conclusion of the input buffer to simplify EOF (End of File) detection.

Skipping comments: In Python, because file iteration handles line endings cleanly, each line ends with \n, producing uniform termination. Java console inputs or strings depend strictly on length checks.

This is where Java diverges from Henley's Python implementation. Rather than complicating the lexer loop with length edge-cases or requiring explicit semicolons, we normalize the input string by appending \n implicitly.

Helper Functions & Lookahead Refinements

We introduce dedicated helpers to classify alphabetic identifiers, numbers, and operators.

Token Generation Logic

We assemble the core getToken() method. Most of the structure mirrors the Python architecture, though Java requires explicit string comparison methods and enum instantiation.

Conclusion

With this, we have completed the first fundamental milestone: a functional lexer that takes source strings, ignores irrelevant whitespace and comments, and emits a clean stream of classified tokens.
